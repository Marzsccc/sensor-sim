# v0.22.0 — Delayed / Out-of-Sequence Measurement Fusion (OOSM)

*Status: complete. Full suite 252 → 284 passing (32 new).*
*Date: 2026-09-19 (nightly autonomous task).*

## Why

Everything in the stack so far — v0.4 latency model, v0.5 display-time
prediction, v0.9 marker projection — treats delay as a *rendering* problem:
fuse whatever arrived, then predict forward to the display instant.  That is
correct only when the fused state is honestly stamped at the *measurement*
time.  A naive pipeline that fuses at **receive** time stamps the state with
the arrival clock while the numbers describe a scene that is already one
sensor latency old, and no amount of forward prediction recovers it — the
estimate is a *biased* function of a stale scene, not a delayed version of
the right one.

That is the AR-HUD "marker trails the world" symptom in its second, less
obvious form, and it is worst exactly where it hurts: a fast, precise sensor
(camera, 60 ms) interleaved with fast, coarse ones (radar 30 ms, odometry
5 ms), so late frames arrive *after* newer samples have already been fused —
out of sequence, not merely late.

The roadmap item ("measurement-time fusion with out-of-order reprocessing")
was the last unaddressed latency gap in the library.  v0.22.0 closes it.

## What changed

### New module `sensor_sim/delay_fusion.py`

Self-contained (no radar/tracker/camera imports) so it can back any linear
fusion front-end, and small enough to read in one sitting.

| Piece | Role |
|---|---|
| `DelayedMeasurement` | `(t_meas, t_recv, z, H, R, sensor)` — validity time *and* arrival time. Rejects `t_recv < t_meas`. |
| `CVModel` | Time-invariant constant-velocity model, arbitrary position dim `n`, state `[p, v]` (`2n`). `F(dt)`, `Q(dt)` (continuous white-acceleration, per-axis PSD `q`), plus `observe_position(sigma)`. `F_fn`/`Q_fn` hooks allow swapping the dynamics without touching the filter. |
| `DelayedFusionFilter` | Linear KF with a bounded state/measurement history. Out-of-order sample ⇒ rewind to the nearest stored state at or before `t_meas`, apply it, replay every later measurement forward. |
| `FusionDiagnostics` | `n_received / n_accepted / n_out_of_order / n_reprocessed / n_pruned / max_rewind_s` — the numbers the demo reports. |
| `position_covariance`, `nees_position` | Read-out helpers (position block, 2n-dof NEES). |

### The exactness property (the whole point)

For a **linear time-invariant** system, rewind-and-replay reproduces *exactly*
the estimate an in-order filter would have produced — to floating-point
tolerance.  This is not "close enough"; it is an equality that the test suite
asserts at `atol=1e-9`:

* `TestExactness::test_out_of_order_matches_in_order` — random per-sample
  delays, arrival order ≠ validity order ⇒ state and covariance match the
  in-order reference.
* `TestExactness::test_reverse_order_matches_in_order` — fully reversed
  arrival order (the worst case) ⇒ identical.
* `TestExactness::test_duplicate_times_stay_stable` — two sensors stamped at
  the same instant stay finite.

The Joseph-form covariance update plus a symmetric re-average keeps `P`
PSD-safe across hundreds of replays.

### Clock semantics (documented, and tested)

`DelayedFusionFilter.t` is the **newest fused measurement (validity) time**,
not the host wall clock.  Three consequences, each pinned by a test:

1. A stream that is **delayed but monotone** in validity time is *in
   sequence* — it never rewinds.  The state carries the sensor timestamp and
   the residual latency is removed at the display instant by
   `predict_to_time` (this is the AR-HUD split: fuse at measurement time,
   render at display time).
   → `test_uniformly_delayed_monotone_stream_needs_no_rewind`
2. A sample is out of sequence **only** when its validity time precedes the
   newest fused time — the interleaved multi-rate case.
   → `test_interleaved_multirate_stream_is_stable`
3. After a rewind the clock is **restored**, not dragged back: a late sample
   corrects the past without rewinding "now".
   → `test_clock_stays_at_newest_validity_time_after_rewind`

`mode="receive_time"` is kept as the naive baseline so a pipeline can be
A/B measured rather than argued about.

## Production traps caught during validation

These are the reason the module is worth more than its line count:

1. **History amputation (regression test).**  The first `_reprocess()`
   rebuilt `_snapshots` from the anchor onward, silently discarding every
   earlier snapshot.  After a long run of late samples the history collapsed
   to a couple of entries and the next rewind raised `RuntimeError` — a
   failure that only shows up after minutes of runtime, i.e. in the field.
   Fix: carry the strictly-older prefix over and rebuild only the suffix.
   → `test_history_survives_repeated_out_of_order_updates` (300 forced
   rewinds, then asserts the retained span is still ≈ `history_s` and one
   more rewind near the window edge still works).

2. **The "delayed" red herring.**  While writing the regression test it
   became clear that a *uniformly delayed* stream does **not** rewind at all
   under measurement-time semantics — so a naive test would have "proved"
   reprocessing works while exercising zero rewinds.  The test was rewritten
   to interleave an in-order fast sensor with a permanently 100 ms-stale one,
   which is what actually forces replay.  Documented in the test docstring.

3. **Pruning must never drop the newest snapshot.**  `_prune()` keeps the
   latest snapshot unconditionally, so a filter with a short `history_s` and
   a sparse stream stays readable (`test_pruning_keeps_latest_state_usable`)
   while still raising honestly when a rewind is genuinely beyond history
   (`test_old_out_of_order_beyond_history_raises`).

## Demo — `examples/delay_fusion_demo.py`

Scene: target on a circle, `r = 25 m`, `ω = 0.35 rad/s` (≈ 8.75 m/s); three
position sensors delivered in *receive* order:

| sensor | rate | delay | σ |
|---|---|---|---|
| odom | 100 Hz | 5 ms | 1.20 m |
| radar | 20 Hz | 30 ms | 0.60 m |
| camera | 10 Hz | 60 ms | 0.25 m |

1040 measurements.  Both pipelines are scored at the *same* wall-clock
display instant (`t_recv + 60 ms`) — comparing each against its own clock
would hand the naive filter a shorter horizon for free.

```
metric                                receive_time            oosm
------------------------------------------------------------------
streaming position RMSE [m]                  0.440           0.273
mean effective lag [ms]                        0.0             6.3
display-time (+60ms) RMSE [m]                0.480           0.339
mean position NEES (2 dof)                   6.791           1.877
out-of-order samples                             0             238
reprocessed updates                              0             956
max rewind [ms]                                0.0            80.0
```

Readings:

* **Streaming RMSE −38%** (0.440 → 0.273 m) and **display-time RMSE −29%**
  (0.480 → 0.339 m) — the naive filter loses on both halves, so this is not
  a case of "trade streaming for display".
* **NEES 6.79 → 1.88.**  The 2-dof expectation is 2.  The naive filter is
  *over-confident by 3.4×*: its covariance says "I am sure" about a state it
  has biased.  This is the more dangerous failure mode — an over-confident
  HUD fades markers in when it should fade them out.  OOSM is nearly
  consistent.
* **238 out-of-order samples / 956 reprocessed updates / 80 ms max rewind**
  — i.e. the naive mode reports zero of these because it cannot see them.
* Mean effective lag 6.3 ms in OOSM is not residual error: it is the honest
  gap between the newest *validity* time and the arrival clock, which
  `predict_to_time` exists to bridge.

streaming vs display-time, effective lag, NEES).

## Where it plugs in

* Upstream of v0.5 `PosePredictor` / v0.9 `AdasPipeline`: feed them a state
  fused at measurement time instead of arrival time, and the display-time
  prediction becomes a pure latency bridge rather than a partial bias patch.
* Feeds naturally into v0.21 `MotAccumulator` grading once the fused track
  set is the thing being scored.
* Remaining limitation, stated honestly: the exactness guarantee is for
  *linear time-invariant* systems.  A nonlinear (ESKF) front-end can reuse
  the same rewind-and-replay skeleton but exactness becomes first-order —
  that would be the natural v0.23 candidate.
