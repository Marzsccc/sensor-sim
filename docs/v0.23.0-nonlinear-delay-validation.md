# v0.23.0 — Nonlinear (ESKF) Delayed-Measurement Fusion: Rewind + Replay

**Scope:** `sensor_sim/nonlinear_delay.py` · `tests/test_nonlinear_delay.py` ·
`examples/nonlinear_delay_demo.py`

**Status:** 35 new unit tests, full suite **319 passed** (was 284).

---

## 1. Why this exists

v0.22.0 (`delay_fusion.py`) fixed delayed / out-of-sequence measurements for a
**linear time-invariant** filter.  That solution rests on linearity:

* the state evolves as `x ← F x` and updates compose as matrix products;
* therefore "rewind to the state at or before `t_meas`, apply the late
  measurement, replay every later one" provably reproduces the in-order
  estimate **exactly** (asserted at `atol=1e-9`).

The real vehicle stack is not linear.  The GNSS+IMU filter in `eskf.py` runs a
strapdown mechanisation with quaternion products and a body↔world rotation, and
propagates its covariance through a linearised error state.  So the obvious
question was open:

> Does the rewind-and-replay idea survive contact with a nonlinear,
> inertial-driven estimator — or does it silently degrade into "approximately
> right, sometimes"?

Answer: **it survives exactly**, provided the replay re-feeds the *raw inertial
samples*, not just the state.  This release adds that, and measures it.

---

## 2. The key insight

The ESKF's nominal-state propagation is a **deterministic function of the IMU
sample sequence**.  Identical samples in identical order ⇒ identical states.

So the state history alone is not enough to rewind a nonlinear filter — you
must also retain the *inputs*.  Two buffers replace v0.22.0's one:

| Buffer | Contents | Bounds |
|---|---|---|
| snapshots | `(t, p, v, q, b_a, b_g, P, n_updates)` at every IMU boundary | `history_s` |
| IMU samples | `(t, acc, gyro)`, monotonically increasing | `history_s` |
| GNSS records | `(t_meas, pos, vel, R, t_recv)` | `history_s` |

A late fix then runs:

```
anchor  = newest snapshot with t <= t_meas
restore(anchor)
for each event in merge(IMU buffer, pending GNSS fixes) sorted by validity time:
    IMU  -> mechanise; snapshot
    GNSS -> update
assert state.t == t_before_rewind      # replay is timeline-neutral
```

Two properties fall out, and both are asserted in the tests:

1. **Exactness.** The replayed run visits the same IMU samples in the same
   order as an in-order pipeline, so the estimate matches a plain
   `ESKF` fed in validity order to `atol=1e-9` — including a deliberately
   scrambled delivery order and a two-sensor interleaving that forces 100+
   rewinds.
2. **Determinism.** Because every replay restarts from the *same* anchor and
   walks the *same* buffer, the result depends only on the **set** of fix
   validity times — not on their delivery order — and the clock always lands
   exactly back where it was.

> Note the honest scope: only the *covariance* linearisation is approximate
> (as it always was in an EKF).  The mechanisation is replayed exactly.

---

## 3. A clock-semantics correction worth remembering

v0.22.0 documented: *"a delayed-but-monotone stream never rewinds."*  That was
true **there**, because the fusion-only filter's clock *was* the newest fused
measurement time — so if nothing had been fused, nothing had been stamped.

With an IMU in the loop, the clock is the newest **integrated inertial** time,
which always races ahead of a delayed aiding fix.  Consequently every delayed
GNSS sample *is* out of sequence, and rewinds are the normal case rather than
the exception:

| Pipeline | clock source | delayed monotone fix |
|---|---|---|
| v0.22.0 fusion-only | newest fused measurement | in sequence, no rewind |
| v0.23.0 ESKF | newest integrated IMU sample | out of sequence, rewinds |

This is not a regression; it is the correct behaviour, and the initial test
asserting the v0.22.0 behaviour failed until it was rewritten. Worth keeping as
a lesson: **clock semantics are a property of the whole estimator, not of the
fusion trick**.  Residual latency at render time is still removed by
`extrapolate_to()` — the AR-HUD split (fuse at measurement time, render at
display time) is unchanged.

One more invariant held: a rewind **never drags the clock back**.  `t` is
restored to exactly its pre-rewind value, regardless of how deep the rewind
went.

## 4. API surface

```python
from sensor_sim import RewindReplayESKF, GnssMeasurement, ImuSample

f = RewindReplayESKF(mode="oosm", history_s=5.0)
f.initialize(t0, p0, v0, q0)

f.add_imu(t, acc, gyro)                      # monotone inertial input
f.add_gnss(t_meas, pos, vel, t_recv=...)     # late fixes handled internally

p_now, P_pos = f.extrapolate_to(t_display)   # render instant + covariance
```

| Symbol | Role |
|---|---|
| `RewindReplayESKF` | ESKF wrapper with measurement-time fusion |
| `ImuSample` / `GnssMeasurement` | validated records (shape + `t_recv >= t_meas`) |
| `EskfSnapshot`, `capture_state`, `restore_state` | exact state round-trip; snapshots are copies, never views |
| `position_nees` | 3-dof NEES for reporting |
| `RewindDiagnostics` | `n_imu`, `n_gnss`, `n_rewinds`, `n_imu_replayed`, `max_rewind_s`, `n_clamped`, … |
| `mode="receive_time"` | the naive baseline, kept so a pipeline can be A/B measured instead of argued about |

`extrapolate_to()` rejects a non-finite `t_future`.  This is not cosmetic: a
caller that computes `t_recv + 0.06` while `t_recv = inf` (i.e. "is any more
data coming?") previously obtained a NaN pose through `0 * inf` in the
velocity term.  NaN poses propagate silently into a renderer; a `ValueError`
does not.

## 5. Measured effect

`examples/nonlinear_delay_demo.py` — 25 m/s (90 km/h) vehicle, lateral sinusoid
(1.5 m/s² at 0.5 rad/s), 100 Hz IMU, 10 Hz GNSS with **200 ms** latency,
1500 IMU samples / 138 fixes.  Both pipelines are scored at the **same**
wall-clock display instant (`t_recv + 60 ms`), so the lagging pipeline gets no
free shorter prediction horizon.

| Metric | `receive_time` (naive) | `oosm` (rewind+replay) |
|---|---|---|
| Streaming position RMSE | **4.904 m** | **0.719 m** |
| Display-time RMSE (`t_recv+60 ms`) | 4.916 m | 0.783 m |
| p95 position error | 5.532 m | 1.341 m |
| Mean position NEES (3 dof, expect 3) | **121.40** | **1.95** |
| Rewinds | 0 | 138 (max 200 ms) |
| IMU samples replayed | 0 | 2661 |

**The prediction checks out.** `v · delay = 25 m/s × 0.2 s = 5.01 m`, and the
naive pipeline's RMSE is **4.904 m** — the error is the delay bias itself, not
a precision loss.  The naive/OOSM ratio is **6.8×**.

**The NEES gap is the more damning number.** 121 vs 1.95 against an expectation
of 3: the naive filter is not merely inaccurate, it is *catastrophically
over-confident* — it asserts metre-level certainty about a state that is 5 m
wrong.  For an AR-HUD that is the dangerous direction: an over-confident
estimator keeps a marker solidly drawn when it should be faded or withheld.
This mirrors v0.22.0's 6.79-vs-2 finding and generalises it from the linear
fusion stage to the inertial one.

Also note the display-time column: forward extrapolation does **not** rescue
the naive pipeline (4.904 → 4.916 m).  This is the central teaching point of
both releases — *latency baked in as bias cannot be predicted away.*

## 6. Bugs found while building this

Three, each with a regression test now in place:

1. **`extrapolate_to(inf)` returned NaN.**  `0 * inf` in the velocity term.
   Fixed with an explicit finiteness check (§4).  Found by the demo's own
   control flow, not by a unit test — a reminder that demo scripts are tests.
2. **Test-side tie-break mismatch.**  The replay merges IMU and GNSS events by
   timestamp; a fix stamped *exactly* at an IMU boundary must be applied
   *after* that boundary's mechanisation, and floating-point accumulation in
   `t += period` made a naive comparison flip the order.  Both the filter and
   the reference runner now key on `round(t, 9)`.  The filter behaviour was
   correct; the *reference* was subtly wrong — which is precisely why the
   reference is built independently on the bare `ESKF` rather than by reusing
   the code under test.
3. **A class-scoped pytest fixture declared as an instance method.**  It ran,
   but pytest warned that the attributes would not be visible to the test
   methods.  Converted to a `@classmethod`.

| `TestClockSemantics` | 5 | clock never dragged back; replay lands exactly on prior time; extrapolation grows covariance and matches constant velocity; rejects past/inf |

| `TestNaiveVsOosm` | 7 | on a physically consistent track: naive lags, ≥2× worse, ≥3× over-confident, OOSM NEES in the right ballpark, error scales as `v·delay`, bounds respected |

The long-run test is the direct descendant of v0.22.0's nastiest bug: an early
implementation rebuilt its snapshot list from the anchor on every rewind,
silently amputating all older history, so that after a few minutes of
out-of-order samples every rewind raised `RuntimeError`.  Here 299 consecutive
rewinds are run with `history_s=2.0` and the retained horizon is asserted, plus
a deep rewind afterwards that must not be clamped.

## 8. Where this plugs in

Downstream of `eskf.py`, upstream of the display stage:

```
IMU  ──┐
       ├─► RewindReplayESKF ──► extrapolate_to(t_display) ──► marker render
GNSS ──┘        ▲
                └── replay bridge for late fixes (this release)
```

The same skeleton generalises to any delayed aiding sensor with a replayable
input: wheel odometry, vision pose, map matching.  The requirement is only that
the filter's propagation be deterministic given its inputs.
