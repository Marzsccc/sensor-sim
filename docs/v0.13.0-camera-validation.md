# v0.13.0 — Camera Feature & Optical-Flow Simulation

**Module:** `sensor_sim/camera.py` · **Demo:** `examples/camera_demo.py`
**Tests:** `tests/test_camera.py` (+14, total 124 passing)

## Problem (the vision sensing layer the stack needed)

The simulator already produces IMU, GNSS, wheel odometry, latency/time-sync,
display-time prediction, uncertainty, outages, ADAS marker projection,
visibility/occlusion, hazard arbitration and (v0.12.0) LiDAR point clouds.  But
the vision/VIO side was still missing: a **camera** that turns 3D world
landmarks into pixels and, crucially, the **optical flow** a feature tracker /
VO front-end actually consumes.  This module closes that gap with a forward
pinhole camera that projects analytic world features and tracks them across
frames -- directly relevant to monocular/VIO and AR-HUD reprojection work.

## Design

| Piece | Role |
|---|---|
| `CameraConfig` | Pinhole intrinsics (`fx/fy/cx/cy`), resolution, radial distortion (`k1`), depth-range clip `[min_z, max_z]`, pixel noise sigma, dropout probability. |
| `FeaturePoint` | A world landmark with a stable `feature_id` (for cross-frame association), a resting `pos_w`, owner `object_id`, and optional constant `velocity` (dynamic features move in time). |
| `CameraSensor` | Composes the body mount + trajectory pose into world→sensor with `_quat_to_rotmat` (same convention as `MarkerProjector` / `LidarSensor`). `project()` maps sensor +x-forward / +y-right / -z-down points to pixels; `observe()` filters in-front / in-image / not-dropped features and adds pixel noise. |
| `track(p0, p1, ·) ` | Observes the same world from two host poses, associates by `feature_id`, and returns per-feature previous/current pixel position, pixel displacement (optical flow), current depth and pixel velocity (px/s). |

The camera reuses the exact same world / body / sensor frame conventions and
`R_bw` plumbing as `CameraProjector` and `LidarSensor`, so image features,
markers and point clouds all live in one spatially-consistent stack.

## Validation

- **On-axis projection:** a feature dead ahead on the optical axis lands
  exactly at `(cx, cy)`; an off-axis feature at `+y` shifts `u` by `fx·y/z`
  (600·1/10 = +60 px, measured exactly).
- **Vertical direction:** world +z (up) maps to smaller `v` (image v points
  down) -- sign convention correct.
- **Culling:** features behind the camera (`x<0`), outside the image, or
  outside `[min_z, max_z]` are dropped.
- **Flow from ego motion:** static ego + static feature → zero flow; ego
  translating laterally +y at fixed depth → feature shifts right (`flow_u>0`);
  forward ego motion shrinks depth (20 → 19 m) with finite pixel velocity.
- **Noise / dropout:** raising `pixel_noise_sigma` widens projected scatter;
  raising `dropout_prob` (0.0 → 0.9) drops the feature.
- **Mount:** mounting the camera +1 m in +y shifts the chief ray so an
  on-axis feature lands left of `cx`.
- **Distortion:** positive `k1` pushes an off-axis point further from `cx`
  than the undistorted projection.

## Demo output (10 m/s forward drive)

| feature | obj | u0 | v0 | u1 | v1 | flow_u | flow_v | depth(m) |
|---|---|---|---|---|---|---|---|---|
| 0 (near) | static | 480.0 | 480.3 | 471.3 | 486.1 | −8.7 | +5.8 | 9.5 |
| 4 (far) | static | 531.1 | 414.0 | 527.7 | 415.3 | −3.4 | +1.2 | 21.5 |
| 100 | **pedestrian** | 340.1 | 410.0 | 326.3 | 413.3 | **−13.9** | +3.3 | 7.5 |

- **Depth-speed coupling is physical:** the near feature (9.5 m) flows ~2.5×
  faster than the far one (21.5 m) -- the classic inverse-depth optical-flow
  scaling.
- **Ego-motion expansion (FOE) is correct:** left features flow left
  (`flow_u<0`), right features flow right (`flow_u>0`) — expansion away from
  the forward focus of expansion.
- **Motion segmentation:** the walking pedestrian (id 100) shows a much
  stronger, distinctive flow vector than the static background at a similar
  depth — exactly the cue a VO front-end uses to separate dynamic objects from
  ego motion.

## Production notes

- **Feature-id association is the honest contract.**  The returned `FlowFrame`
  is keyed by stable `feature_id`, so downstream can build a landmark track
  across many frames (the foundation of a real VO/VIO backend) rather than
  re-deriving matches from pixel proximity.
- **Same pose plumbing as LiDAR/markers.**  Because the camera, LiDAR and ADAS
  projector share `_quat_to_rotmat` + `mount_t_body`, fusing image features and
  point clouds into one ESKF/pose estimate needs zero frame realignment.
- **Dynamic-vs-static is the interesting signal.**  The demo shows the same
  class of ambiguity AR-HUD / VIO faces: disentangling target motion from ego
  motion from raw feature flow.  A natural follow-on is a two-frame
  decomposer that separates translational-from-rotational and static-from-
  dynamic flow, which would feed directly into the existing ESKF outlier
  gating / uncertainty modules.
