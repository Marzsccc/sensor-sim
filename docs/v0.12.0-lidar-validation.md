# v0.12.0 — LiDAR Point-Cloud Simulation

**Module:** `sensor_sim/lidar.py` · **Demo:** `examples/lidar_demo.py`
**Tests:** `tests/test_lidar.py` (+10, total 110 passing)

## Problem (the sensing layer the rest of the stack needed)

The simulator already produces IMU, GNSS, wheel odometry, latency/time-sync,
display-time pose prediction, uncertainty propagation, GNSS outages, ADAS
marker projection, visibility/occlusion and hazard arbitration -- a complete
fusion + AR-HUD stack.  But every downstream module still had to *hand-place*
a world object (a lead vehicle, a barrier) and project it analytically.  There
was no way to generate the raw **range measurements** a physical sensor would
return, so there was no way to exercise SLAM/segmentation/fusion against
realistic, noisy point clouds.  This module closes that gap: an analytic
raycasting LiDAR over a primitive world.

## Design

| Piece | Role |
|---|---|
| `GroundPlane` / `Box` / `Sphere` | Analytic world primitives. Each implements `_hits(origin, direction, center) -> nearest t or None`; `world_pos(t)` adds a constant `velocity` so any object can be dynamic. |
| `LidarConfig` | Scan geometry (`spinning` 360° vs `solid` rectangular FOV), beams × columns, `[range_min, range_max]`, range-noise sigma, dropout probability. |
| `LidarSensor` | Houses the ray grid and the mount offset. `scan(point, world, t)` casts every ray in the *body* frame, rotates it to world with `R_bw` (world←body quaternion), raytraces against every primitive, clamps, applies noise + dropout, and returns a `LidarFrame`. |
| `LidarFrame` | `points` (sensor frame), `ranges`, `intensities` (reflectivity), `object_ids` (which primitive — ground is 0, primitives get 1, 2, …), plus per-point azimuth/elevation. |

The mount handling reuses the exact same convention as `MarkerProjector`:
the sensor sits at `mount_t_body` in the body frame and is composed into the
world frame via the trajectory quaternion.  That means the point clouds are
immediately consistent with the ESKF/pose/uncertainty modules above them.

## Validation

- **Ground-plane range:** a downward ray from 1.5 m above the plane returns
  exactly 1.5 m (analytic check).
- **AABB front-face:** a 1 m-half-extent box centered at (10,0,0) is hit by the
  forward central beam at 9.0 m (measured 9.03 m including mount offset).
- **Range clamping:** a box beyond `range_max` produces zero points; within
  range, every reported range ≤ `range_max`.
- **Dynamic object:** a box at (10,0,0) with velocity (5,0,0) m/s shifts its
  point-cluster centroid ~5 m along +x between t=0 and t=1 (measured 9.5 →
  ~14.5 m centroid travel in the body frame over the scan).
- **Noise behaviour:** raising `range_noise_sigma_m` from 0.001 → 0.2 m visibly
  increases the std of measured ranges> (energy check).
- **Dropout:** raising `dropout_prob` from 0.0 → 0.5 monotonically reduces the
  number of valid points.
- **Geometry:** `spinning` (columns across ±π) sees a box on all sides;
  `solid` with a narrow FOV does **not** see a box 90° off-axis.

## Production notes

- **Body-frame output is the honest contract.**  Downstream consumers fuse in
  the *sensor* frame (that is what a real driverless stack sees); transforming
  to world is the caller's job with the same `R_bw` used for the scan, which
  keeps this module drop-in consistent with `predict.py` / `adas.py`.
- **Analytic primitives are the first fast board.**  A follow-on roadmap item
  moves to camera images (optical flow / feature reprojection); the same
  world + pose plumbing (`world_pos`, `R_bw`) is designed to be reused so the
  camera and LiDAR stay spatially consistent.
- **Dynamic smear models perception reality.**  A constant-velocity object
  crossing the beam leaves a *moving cluster*, not a static one — a reminder
  that raw LiDAR segmentation must disambiguate ego-motion from target motion,
  the same class of challenge the AR-HUD latency work addresses.
