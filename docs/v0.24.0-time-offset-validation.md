# v0.24.0 — Online Sensor Clock-Offset Estimation (observability, and how the filter first fooled itself)

**Scope:** `sensor_sim/time_offset.py` · `tests/test_time_offset.py` ·
`examples/time_offset_demo.py`

**Status:** 76 new unit tests, full suite **395 passed** (was 319).

---

## 1. Why this exists

v0.22.0 and v0.23.0 solved *when* to fuse a measurement: fuse at the measurement
time, rewind and replay if it arrives late.  Both releases share a hidden
assumption, stated explicitly in their own docs:

> the sample's capture time is **known**.

In a vehicle it is not.  The GNSS receiver, the camera and the wheel-encoder ECU
each run their own oscillator; the host reads their stamps as if they were host
time.  A receiver clock that is 120 ms fast stamps every fix 120 ms *late*, so
the fix describes a scene two lane widths behind reality at 22 m/s — and no
amount of rewind/replay fixes it, because the **input timestamps themselves**
are wrong.  `latency.py` already models such clocks (`SensorClock`) and offers
the IEEE 1588-style offline fix (`TimeSync`), but that needs paired timestamps
(a PPS or a bidirectional link).  A vehicle has neither: only a body that moves
and a stream of fixes.

This release estimates the offset **online, jointly with the state**.

Note what is *not* new here: the *idea* of augmenting a filter state with a
clock bias is old (it is standard in SLAM/INS with time-synchronisation
papers).  What this release adds for the project is the **observability
analysis, the failure modes, and a tested implementation whose uncertainty
tracks the information-theoretic bound** — plus one honest bug story (§6).

## 2. The measurement model

One line of algebra does all the work.  If the sample's true capture time is
`t_rep - b` and the filter's state is stamped at the reference time `t`, the fix
predicts

```
h(x) = p + v * (tau_hat - t),     tau_hat = (t_rep - b + d*t_ref)/(1+d)
     = p - v*b + O(b^2)           (d = rate error, ppm*1e-6)
```

so `dh/db = -v/(1+d)`: **the offset enters the innovation through velocity and
nothing else.**  Every observability statement below follows from that.

## 3. What is observable — and what is not

The tempting summary "no motion ⇒ no information, motion ⇒ information" is
wrong, and getting it wrong is the classic calibration trap.  Three regimes:

| regime | offset observable? | why |
|---|---|---|
| **standstill** (`v == 0`) | no | `dh/db = 0`: no update can shrink `P_bb`. Also *harmless*: the induced error is `v*b = 0`. |
| **constant speed** | no | shift the clock by `b` and the trajectory start by `v*b`: **bit-identical** measurements (asserted exactly in the tests). A constant-speed highway drive cannot calibrate a clock offset, however long. |
| **varying speed + an independent reference-clock motion source** | yes | the reference channel pins the trajectory *shape*, which a time-shift cannot reproduce. |

With the free initial position marginalised out, the Fisher information from
position fixes is

```
I(b) = sum((v_k - mean(v))^2) / sigma^2        =>   sigma_b >= sigma / sqrt(sum((v-vbar)^2))
```

i.e. it is the **variation** of speed that carries the information, not its
magnitude.  The demo's drive (0 → 22 m/s with manoeuvres, 1 m GNSS) drives the
bound to **3.9 ms**; the estimator's own `P_bb` lands at **5.1 ms** and the
ensemble scatter over 9 seeds at **8.5 ms** (the bound assumes the reference
speed is exact; here it is a 20 Hz encoder with 0.05 m/s noise and the truth is
only piecewise constant-velocity).

Helpers `bias_fisher_information()` and `crlb_bias_std()` expose this, and are
tested against the closed form — including that **constant speed returns
`inf`**.

---

## 4. Two structural requirements the tests now pin down

**(a) The filter clock must be driven by the reference-clock channel.**
`update_velocity()` (wheel odometry / CAN speed / IMU) advances the clock;
`update()` never does.  This is not a style choice — see §6.

**(b) The offset is only identifiable alongside a reference-clock motion
source.**  With no independent velocity, no trajectory shape helps: the tests
show the posterior staying at the prior and following it when the prior moves.

## 5. API surface

```python
from sensor_sim.time_offset import ClockOffset, OffsetAugmentedFilter, crlb_bias_std

clk = ClockOffset(bias_s=0.120, rate_ppm=30.0)     # simulation side
t_rep = clk.to_reported(t_true)                     # what the sensor stamps

f = OffsetAugmentedFilter(CVModel(n_dim=1, accel_psd=5e-2),
                          x0=np.array([p0, v0]), P0=np.diag([1e2, 1e-2]),
                          bias_std0=0.5)            # vague prior: offset < 0.5 s
f.update_velocity(t_ref, z_v, sigma_v)              # 20 Hz, reference clock  <- drives the clock
f.update(t_rep, z_pos, sigma)                       # 10 Hz, skewed clock     <- fixed, not fused "now"
f.bias, f.bias_std, f.rate, f.rate_std             # estimates (+-1 sigma)
f.offset_at(t_rep), f.true_time(t_rep)              # staleness / corrected capture time
f.diag.as_dict()                                    # n_updates, n_ahead, n_behind, n_velocity_updates, ...
```

State layout `x = [p (n), v (n), b, (d)]`; the kinematic block reuses
`delay_fusion.CVModel`, the clock states are random walks (with the correct
`b`-integrates-`d` cross terms).

## 6. How the estimator first fooled itself (and the fix)

The first implementation advanced the filter clock with the **skewed** stream
(`predict_to(t_rep)` inside `update`).  It looked reasonable and it "worked" —
for positive offsets.  A parameter sweep across `b_true` showed:

```
b_true = -0.20 -> b_hat = -0.97      b_true = +0.10 -> b_hat = +0.10
b_true = -0.10 -> b_hat = -0.31      b_true = +0.20 -> b_hat = +0.19
b_true = -0.05 -> b_hat = -0.24      b_true = +0.30 -> b_hat = +0.30
   ... and every one of them reported sigma_b ~ 5 ms.  Confidently wrong.
```

Diagnosis, in three steps:

1. A **noise-free cost grid** over (fixed `b`, fixed start-position shift)
   showed the objective is *not* bimodal — it has a **flat valley**: for
   `b >= b_true` the cost is exactly zero.  So the estimator was not stuck in a
   bad local minimum; the problem was degenerate.
2. The degeneracy is physical once you see it: with the clock driven by the
   skews, a `b_hat` that is too large makes every *reference-clock* velocity fix
   land **behind** the state's clock — and a lagged velocity stream reconstructs
   a lagged trajectory, which is exactly what a too-large `b` needs.  Wrong
   answer, perfect fit.  The valley is one-sided because a clock that *leads*
   has no such "lag" to hide in — hence the sign asymmetry.
3. Driving the clock from the reference stream removes the valley: the
   estimator becomes symmetric and accurate across `[-0.3, +0.3] s`
   (multi-seed error < 3 ms, and the sign sweep is flat).

The lesson generalises the one v0.23.0 recorded: **clock semantics belong to
the estimator, not to the fusion trick.**  The tests
(`TestClockIsDrivenByReference`) now pin the correct behaviour, including that
`update()` leaves `f.t` untouched.

A second hypothesis was tested and **rejected** — worth recording because it
looked convincing: that the odometry-driven position propagation (a left-Riemann
integral, one tick lag) would masquerade as a clock offset of half a tick.  In a
noise-free run the estimate is *exact* (error +0.1 ms) and **independent of the
odometry rate** (0.01 / 0.02 / 0.05 s), because the position fixes keep the
position pinned and the residual is proportional to acceleration, not speed.  A
"fix" that compensated it made things *worse* (a clean +`dt/2` bias); it is not
in the code.

## 7. Measured effect (demo)

90 s urban drive: standstill 0–15 s, accelerate, slow section, fast section,
stop; 20 Hz wheel odometry on the reference clock; 10 Hz GNSS with 1 m noise and
a +120 ms clock offset.  Three pipelines, same noise realisation:

| pipeline | offset estimate | offset error | pos RMSE (moving) |
|---|---|---|---|
| naive (trust the stamps) | 0 ms (pinned) | −120 ms | **1.551 m** |
| **online (this module)** | 117.4 ms | −2.6 ms | **0.034 m** |
| oracle (knows `b`) | 120.0 ms | 0 | 0.041 m |

* The naive peak bias is the predicted `v*b = 22 m/s x 0.12 s = 2.64 m`.
* Online is **45x** better than naive and even edges out the oracle on position
  RMSE — because the vanishing offset estimate also absorbs residual model
  error.  The oracle remains the honest *offset* reference.
* Ensemble (9 seeds): mean 119.0 ms (error −0.96 ms), scatter 8.5 ms.
* The estimate is flat during the opening standstill, then converges over the
  first acceleration — the "unobservable is also harmless" duality, visible in
  the figure.
* `bias_std` falls from the 500 ms prior towards the 3.9 ms CRLB.

Figure: `examples/time_offset_demo.png` (speed profile; `b_hat ± 2σ` vs truth;
position error per pipeline; uncertainty vs bound). The plotted run is the
**median of a 9-seed ensemble**, not the best one.

## 9. Where this plugs in

* **AR-HUD**: a stale fix is a *systematic* marker offset ``v*b`` that no
  display-time prediction removes (v0.23.0 established the same for delay:
  *bias cannot be extrapolated away*).  This is the calibration step that has to
  happen before any of the other compensations matter.
* **Multi-sensor rigs**: the same estimator generalises to per-sensor offsets;
  only *differences* are observable without an absolute reference, which is why
  the odometry/IMU channel is the timekeeper here.
* **Calibration procedure, from the theory**: to calibrate a timestamp offset
  you need (i) an independent clock-carrying motion reference and (ii) speed
  *variation*.  A constant-speed test drive — the natural thing to do — carries
  zero information, no matter how long it lasts.
