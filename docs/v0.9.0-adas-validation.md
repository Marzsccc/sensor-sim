**Date:** 2026-08-18 (夜间自主任务)

**Status:** ✅ validated

## Motivation

The AR-HUD draws ADAS markers — ACC lead-vehicle box, FCW/AEB hazard wedge,
lane boundaries — anchored to *world* objects that onboard perception
observed at an earlier capture time. Rendering them with the latest fused
ego pose (which itself lags by the camera pipeline delay) pushes the marker
several meters behind the real object and off the lane lines a driver is
following. This is the classic **temporal registration error** in AR
(Azuma 1997), and the fix is the same display-time prediction used in
v0.5.0/v0.7.0: propagate the fused ego pose forward to the display instant
before projecting the marker.

That error is *not* the ego-pose error already measured by `DisplayPipeline`;
it is the **marker reprojection error** — what the driver actually sees.

## What was built

| Component | Purpose |
|---|---|
| `AdasMarker` | Typed world-anchored marker (kind, ref point, optional corner points) |
| `lead_vehicle_marker()` | ACC: 8-corner bbox around a lead-vehicle center |
| `hazard_marker()` | FCW/AEB: hazard point + warning-wedge apex angle / max range |
| `lane_line_marker()` | Lane boundary segment (left/right/center) |
| `MarkerProjector` | `to_body()` world→body (x forward, y right, z down); `screen_xy()` pinhole to HUD pixels |
| `AdasPipeline` | End-to-end loop: naive vs compensated marker render + uncertainty fade |

## Design notes

- **Body frame** x-forward/right/down: `R_wb = quat_to_rotmat(att)` already
  maps world→body, so `p_body = R_wb @ (p_world - pos)`.
- **Screen projection** uses the forward axis (+x) as depth:
  `u = cx + f·y/x`, `v = cy + f·z/x` (z down ⇒ +v down). Nearby markers
  (dangerously close hazards) blow up in pixels, which is physically right —
  and why the radial-meters error is the more stable report.
- **Uncertainty fade:** propagates the 9×9 `[p,v,θ]` covariance through the
  display horizon (reusing `PredictorUncertainty`) and maps the 95%
  horizontal radius to an alpha in `[0,1]`, tuned by `sigma_scale`. Steady
  state ≈ 1.0 (fully opaque); cold-start / outage / large-delay cases fade
  the marker down so it does not over-commit.

## Validation results (straight road, 20 m/s, 50 ms camera delay + 60 Hz display)

Horizon ≈ **66.7 ms** (50 ms pipeline + one display frame).

| Metric | Naive | Compensated | Δ |
|---|---|---|---|
| Lead-vehicle radial err | 1.333 m | 0.100 m | **−92.5%** |
| Hazard radial err | 1.333 m | 0.100 m | −92.5% |
| Lane-right radial err | 1.333 m | 0.100 m | −92.5% |
| Lead-vehicle screen px | 362.7 px | 101.7 px | −72% |
| Lane-right screen px | 190.1 px | 51.5 px | −73% |
| Fade alpha (steady state) | — | 0.995 | ≈ opaque |

The naive lag ≈ `delay × speed = 0.0667 s × 20 m/s ≈ 1.33 m`, exactly what we
measure. After compensation it collapses to ~0.10 m — consistent with the
-92% figures seen in v0.5.0 for ego pose.

## Production traps surfaced (mirrors v0.8.0 style)

1. **Nearby-hazard pixel blow-up:** as range→0 the perspective projection is
   numerically unstable; a real HUD clamps the on-screen displacement and
   relies on range/alarm cues, not pure reprojection. Use the radial-meters
   error as the fidelity metric, not pixels.
2. **Forward-depth convention matters:** the first attempt used the down-axis
   as depth and produced all-NaN pixels. A forward-looking camera/HUD must
   divide by the forward axis (+x), which is non-obvious when the body frame
   is z-down.
3. **Fade vs trust:** fading markers purely on pose covariance can hide a
   real hazard during an outage; production blends a *minimum opacity floor*
   for FCW/AEB (the wedge must stay visible regardless of pose quality).
