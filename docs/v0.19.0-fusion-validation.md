# v0.19.0 — Radar + Camera Fusion Tracking: Validation

Commit: (filled at release)

## What was built

`FusedTracker` (new module `sensor_sim/fused.py`): a single constant-velocity
EKF that consumes **radar detections** (`RadarFrame`: range / azimuth /
range-rate) and **camera azimuths** (`CameraFrame`: pixel columns converted
through the camera intrinsics) onto the *same* 4-state track
`[px, py, vx, vy]`.  This is the standard ADAS perception-stack pattern: the
radar provides stable range + Doppler, the camera provides a per-scan
azimuthal measurement that directly observes cross-range motion — the axis
the radar alone is structurally blind to in any single frame.

## Key design decisions

1. **Try before you buy: two updates per tick.**  Each fusion cycle first
   associates radar detections (3-D Mahalanobis, chi-2 11.3), then assigns
   camera features (1-D azimuth innovation, chi-2 3.84) to the surviving
   tracks, *including tracks already updated by radar this tick*.  Two
   sequential EKF updates per scan is exactly how a real low-level fusion
   stack behaves (each sensor contributes its own measurement update).

2. **A real production trap was caught in validation:** the first
   implementation reused the *pre-update* azimuth prediction/Jacobian for the
   camera update of a track that had just been updated by radar.  Because the
   state moves during the radar update, the stale Jacobian caused the camera
   update to over-correct — the pedestrian's lateral velocity estimate blew
   up to ~5-6 m/s instead of 2.2 m/s.  Standard multi-sensor EKF discipline:
   **recompute the predicted measurement and Jacobian from the current state
   before every update**.  The fix (`_cam_update` now recomputes `azhat`/`Hc`
   internally) is documented in the module docstring.

3. **Graceful degradation without mode switches.**  Camera dropout
   (night/glare/occlusion) → the radar update still fires; radar dropout →
   the camera update keeps the track alive.  No explicit mode flag: the
   covariance honestly reflects whichever measurement did not arrive.

## Test evidence (tests/test_fused.py, 10 new tests → 205 total)

### Fusion beats radar alone on lateral kinematics (the headline)

Scene: stationary host, pedestrian crossing left-to-right at x = 35 m,
2.2 m/s.  Same radar scans, same seeds; radar-only vs fused (radar+camera).

| integration time | radar-only vy err (m/s) | fused vy err (m/s) | improvement |
|---|---|---|---|
| 1.0 s | 0.065 | **0.020** | 3.3× |
| 2.0 s | 0.136 | **0.028** | 4.9× |
| 3.0 s | 0.206 | **0.070** | 2.9× |

The camera's azimuth measurement makes the lateral velocity observable much
faster than the radar's azimuth *history* alone.  At 2 s the fused estimate
is ~5× closer to the true 2.2 m/s than radar alone.

### Radar-only robustness preserved

- `test_birth_and_update_from_radar_only`: with the camera off entirely, the
  fused tracker still births/updates tracks from radar alone (identical
  lifecycle to v0.18).
- `test_camera_dropout_degrades_gracefully`: camera goes dark at t = 0.8 s;
  the track keeps estimating the closing motion (~-10 m/s) to the end of the
  run, radar-only, without a mode switch.
- `test_gate_rejects_far_camera_feature`: a camera feature far from every
  predicted azimuth (tight 0.1 gate) is not assigned; the radar update is
  unaffected.
- `test_two_targets_keep_identities_with_camera`: two adjacent closing
  vehicles keep their lane order (no identity swap), matching v0.18.

### Lifecycle & determinism

- `test_reacquisition_gets_fresh_track_id`: target disappears (1-2 s) then
  reappears → new track id (no id reuse).
- `test_fused_config_rejects_nonpositive_noise`: config validation.

## Demo (`examples/fused_demo.py` → `examples/fused_demo.png`)

Same scene with a stronger camera (0.5 px noise, 2% dropout) and a lead
vehicle + crossing pedestrian:

- **Convergence**: the fused lateral-velocity estimate reaches the true
  2.2 m/s within ~0.2-0.3 s and stays within ±0.2 m/s; the radar-only
  estimate oscillates (-1.4 → +2.7 m/s) for the first second and only
  settles around t ≈ 1.1 s.
- **Abeam crossing (t ≈ 2.3 s)**: once the pedestrian passes x = 35 m the
  radar-only tracker loses the lateral velocity entirely (azimuth history
  saturates), while the fused tracker keeps tracking correctly — a direct
  demonstration of why the camera matters precisely where the radar goes
  blind.
- Per-scan camera-update count runs at the full 10 Hz (≈30 updates over the
  3 s run).

## Scope / documented limitations (unchanged from v0.18)

- Planar 2-D state (ground-plane model); elevation ignored.
- One detection per object per sensor per scan; no glint/ghosting.
- Camera features assumed closest-object; no appearance-based
  re-identification.
- Greedy NN association, not JPDA/MHT.
