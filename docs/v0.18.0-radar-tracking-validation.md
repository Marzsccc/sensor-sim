# v0.18.0 — Constant-Velocity EKF Radar Detection Tracking

**Module:** `sensor_sim/tracking.py` · **Demo:** `examples/radar_tracking_demo.py`
**Tests:** `tests/test_tracking.py` (+17, total 185 passing)

## Problem (single-frame radar is blind to cross-range motion)

v0.17.0 added the 77 GHz radar: each scan returns range / azimuth /
range-rate detections.  The v0.17 demo made the structural limitation
explicit — a pedestrian crossing in front of the host sweeps azimuth
continuously while Doppler range-rate stays near zero, because Doppler only
sees the *radial* projection of velocity.  A single scan literally cannot
measure lateral speed: the measurement space is 3-D (range, azimuth,
range-rate) and the planar target state is 4-D (x, y, vx, vy), so the
cross-range velocity component is unobservable in any one frame.

Production ACC / FCW / AEB / RCTA stacks do not consume raw scans — they
consume **tracks** produced by a tracker whose job is exactly to fuse the
azimuth history over time and recover the motion a single frame cannot see.
This release adds that layer: a constant-velocity EKF object tracker over
`RadarFrame` detection lists, plus the track lifecycle (birth / confirm /
coast / delete) that turns noisy detections into a stable target list.

## Design

| Piece | Role |
|---|---|
| `TrackConfig` | `coast_max` (scans a confirmed track may miss before deletion), `confirm_min` (updates needed to confirm), measurement noise `sigma_range/angle/rate`, process noise `process_noise_accel_mps2` (continuous white accel), gate probability (chi-square 3-dof). |
| `Track` | Mutable, tracker-owned state: `id`, `age`, `hits`, `missed`, `confirmed`, world-frame `pos`/`vel` (x, y, vx, vy), covariance `P` (4×4). |
| `TrackingFrame` | Per-scan result: `t`, `n_detections`, `n_tracks`, surviving `Track`s ordered by id.  **Tracks are live objects** — the tracker mutates them in place on later scans, so snapshot `x`/`P`/counters inside your per-scan loop if you need history. |
| `RadarTracker` | `process(frame, pos_w, att_q, vel_w)`: predict → associate → update → birth/delete.  Owns a mount transform (`mount_t_body`) so radar-relative detections map into world state. |

### Filter model — why the state is *absolute*

The state is the world-frame horizontal position + **absolute** velocity of
the radar reflection point, predicted with a constant-velocity model
`F = [I₂, Δt·I₂; 0, I₂]`.  For any target moving at constant velocity this
predict is *exact regardless of host motion*, because the host pose only
enters the measurement equation.  (An ego-frame tracker must rotate its
state every scan and treats host rotation as process noise; the world-frame
formulation avoids that entirely.)  The host velocity is still used where it
belongs: to map measured Doppler into an absolute radial-velocity
measurement, `v̂_r_abs = v̂_r_meas + v_host·u`.

**Measurement model** (spherical, radar frame → world frame):

```
h(x) = [ range
         azimuth
         range_rate = (v_host - v_target)·u ]      u = (p_target - p_radar)/range
```

with an analytic 3×4 Jacobian.  `H` is validated against a numerical
Jacobian in `test_h_jacobian_matches_numeric` (relative error < 1e-6), and
the EKF loop itself is validated end-to-end on *deterministic* (zero-noise,
fixed-seed) truth kinematics.

**Process noise** is a continuous white-acceleration model `Q =
σ_a²·[Δt⁴/4·I₂, Δt³/2·I₂; Δt³/2·I₂, Δt²·I₂]` — the standard "CV with accel
jerk" compromise.  The default `σ_a = 1.0 m/s²` matches the radar's default
measurement noise (range 0.1 m, angle 0.5°, range-rate 0.15 m/s); the
test-suite uses the same physical pair, **not** a microscopic over-idealised
pair — an over-confident filter with 1e-3 noise sits below the mm-scale
reflection-point-slide model floor of an extended object and orphans its own
detections (found and fixed during development).

### Association & the two-pass rule

Nearest-neighbour with a Mahalanobis gate: a detection is a candidate for a
track iff `d² = νᵀS⁻¹ν < χ²₃(0.99)`, with a small fixed residual allowance
for extended-object reflection-point slide.  Assignment is **two-pass**:

1. **confirmed tracks** claim their best detections first;
2. **tentative tracks** take only the leftovers.

This is the fix for a failure mode discovered during development (the
"newborn death spiral"): a fresh track carries a wide prior (see birth), so
its innovations are ~0 and its Mahalanobis distance beats every converged
track's — pure greedy NN then starves established tracks on every scan.
Giving confirmed tracks priority keeps one clean detection from feeding a
ghost while a 10-scan-old track starves.

### Lifecycle

- **Birth** — an unassociated detection spawns a tentative track (`hits=1`,
  `confirmed=False`).  Position prior: the detection's range/azimuth mapped
  to world, with a *surface range* compensation for extended objects.
  Velocity prior: Doppler gives the **radial** component directly, so the
  prior is `v_radial·u` with `P_vv` small along u but deliberately large
  cross-range — the filter correctly treats lateral speed as unknown until
  the azimuth history resolves it.
- **Confirm** — `hits >= confirm_min` (default 3) promotes the track; after
  that it is only deleted by the coast rule.
- **Coast** — a confirmed track with no assignment increments `missed` and
  keeps predicting (target temporarily occluded / dropped by the radar
  equation).  Deleted when `missed > coast_max`.  Unassigned *tentative*
  tracks are dropped immediately — a single false detection must not linger.
- **Re-acquisition** — a target that disappears long enough to be deleted
  gets a **fresh track id** when it returns (never a silent resurrection of
  the old id), so downstream logic can distinguish continuity.

## Validation

| Check | Result |
|---|---|
| Static target at 60 m | `pos.x = 57.8 ± 0.5` — surface range, not centre (consistent with v0.17). Speed < 0.2 m/s. |
| Closing lead, 10 Hz over 2.8 s | `pos.x` tracks `57.8 − 20t` within 0.5 m; `vel.x = −20 ± 0.3`; relative closing 20 ± 0.3 m/s. |
| **Crossing pedestrian** (stationary host, vy = 2.2 m/s) | single-frame Doppler can't see it, but after temporal fusion `vel.y = 2.2 ± 0.25` m/s and no phantom down-range velocity (`vel.x` < 0.25) — the v0.17 blind spot, recovered.  Demo shows convergence within ~0.5 s. |
| Crossing pedestrian + moving host (30 m/s) | still recovers `vel.y = 2.2 ± 0.35` **absolute** (the world-frame state absorbs host motion). |
| Coast / delete timing | `missed` climbs 1 per scan after the target leaves; alive at 10, deleted on the 11th consecutive miss; tentative tracks die on their first miss. |
| Gate vs. distant detection | a hard 40 m azimuth cutover does **not** snap the old track — it coasts while a *new* track is born for the new object (two tracks coexist, old one deleted later). |
| Two lanes, no swap | two parallel vehicles never exchange lane identities (no association swap). |
| Determinism | identical fixed seeds → bit-identical state (`test_deterministic`). |
| Jacobian | analytic vs numeric `H`, relative error < 1e-6. |
| Unit coverage | 17 tests → suite total 185, all green, deterministic across repeated runs. |

**Demo** (`examples/radar_tracking_demo.py`, saved PNG): stationary host,
lead vehicle closing at 20 m/s from 150 m + pedestrian crossing at 35 m
ahead at 2.2 m/s.  Raw detections appear as dots; the top panel shows range
tracks tracking truth; the range-rate panel shows the blind spot (lead +20
m/s vs pedestrian |Doppler| < 0.4 m/s the whole scene); the lateral-velocity
panel shows the tracker's `vy` estimate rising to ~2.2 m/s — the signal a
single radar scan can never produce.  The far lead also demonstrates dropout
behaviour: at 150 m the radar-equation `P_d ≈ 0.55`, so early detections
come and go and the tentative lead track churns until it closes below ~100 m
(`P_d > 0.85`) and confirms — honest radar behaviour, handled by the
lifecycle.
